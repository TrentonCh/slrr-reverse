What "reproduces" means. The model predicts everything that belongs to statements: which nodes a statement form produces, their order, all jump offsets, all local indices of `declare` / `release` / `local`, the implicit super call, the implicit return, the releases at the end, and the line of every node. What belongs to expressions and symbol resolution it copies from the class under test through a narrow window: whether a name is a `local`, a `field` or a `path n` with segments (and the pool index of each segment), whether a call path is a lone `method` node or a path, and the pool index or bit pattern of string, type, class, resource-id and float operands. The window is only ever the node at the position the emitter has reached, and what comes through it is still checked: a `local` index must be the one the scope model predicts, a member name must be the identifier of the source. So a reproduced tree proves the statement rules for every statement in it, and the comparison is exact: one node more or less inside any statement would shift every jump behind it.

`notes/expressions.md` is the complement of this document: its model predicts the nodes of expressions (names, calls, operands) and leaves the statement-level nodes out of its comparison (`jump`, `jump_false`, `jump_true`, `case`, `pop`, `value`, `push_void`, `ret`, `ret_value`, `release`, `end`). Those are the nodes this document is about. The two studies were made independently and overlap on the local indices, the declaration nodes, the constructor calls, the order of the expressions inside a tree and the lines of expression nodes; where both decide a rule they agree (section 8.1 names the two undecided ones they state differently).

The one tree of the corpus that does not split into statement forms is `Texture.<init>(I)` in a class file without source; its fault is inside an expression (a `call` followed by a bare `local`, already listed in the foundation). No statement-level node pattern is left unattributed (section 10).

## 2. The shape of a tree

### 2.1 Four kinds of tree

A tree belongs to one field (its initialiser) or one method (foundation 3.5). `tree_shape.py` reads the first and last nodes of all 9,772 trees; none falls outside the patterns below (0 outside).

| Kind | Trees | Empty (0 nodes) | How it ends | Holds for |
| --- | ---: | ---: | --- | ---: |
| Field initialiser | 3,117 | 0 | `E(init)`, `end` | 3,117 of 3,117 |
| Constructor | 3,114 | 70 | `ret`, `R(L-1..0)`, `R(L-1..0)` | 3,044 of 3,044 |
| Method returning `void` | 2,213 | 58 | `push_void`, `R(L-1..0)`, `ret_value`, `R(L-1..0)` | 2,155 of 2,155 |
| Method returning a value | 910 | 2 | ..., `ret_value`, `R(L-1..0)` | 908 of 908 |
| Native method | 418 | 418 | - | - |

`R(a..b)` is the run `release a`, `release a-1`, ..., `release b`; `L` is the number of locals live at the closing brace of the body (`this`, the parameters, the locals declared directly in the body). `E(x)` is the node sequence of expression `x`.

### 2.2 A method tree, front to back

```
constructor only:   the super / this call
                      written out:  E(arg 1) ... E(arg n), push_int n, super_init | this_init, stmt ctor
                      not written:  push_int 0, super_init, stmt ctor
all:                the statements of the body, in order
void method:        push_void, R(L-1..0), ret_value       the implicit return
constructor:        ret, R(L-1..0)                        the implicit return
value method:       (nothing)
all:                R(L-1..P)                             end of the body block: its own locals
all:                R(P-1..0)                             end of the method: parameters, then this
```

`P` is the number of slots the frame starts with (`this` in instance methods and constructors, plus the parameters). Nothing at the top of a tree declares `this` or the parameters: they are in the frame when the code starts (section 3). The nodes behind the last `ret_value` / `ret` are not reached in any tree of the corpus; the compiler emits them all the same, because it closes the scope of the body block and of the method after the statements regardless of what the last statement was. That is why the foundation saw "the release sequence twice": once as part of the return (every return releases all live locals, section 4), once as the two scope ends.

**Proven**: 2,745 constructor trees, 2,494 method trees of the oracle pairs are emitted from this layout and equal the class (`check_stmt.py`); the tail patterns of the table hold for all 9,224 trees with nodes, source or not (`tree_shape.py`); the implicit super call is emitted for 211 constructors whose body does not start with `super(` or `this(`, against 2,457 that start with `super(` and 13 with `this(`.

The implicit return is tied to the kind of method, as far as the corpus can tell: all 2,681 constructors and all 1,746 `void` methods with statements have it, none of the 592 value methods has it. Two readings fit equally: "for constructors and void methods" and "unless the last statement is a return". They differ only for a void method or constructor that ends in `return;` (0 in all sources, with or without class) and for a value method that does not end in a return (0 in all sources); neither occurs, in the class files without source either (no tree ends in two returns one behind the other). **Unknown**, and without consequence for any source of this install.

**Proven** on those counts (all reproduce). A method whose block is empty gets no implicit return and no releases; a constructor whose block is empty is not empty, because the implicit super call is a statement. The fifth word of the method row (locals) is 0 for every empty tree. A method body that holds statements which emit nothing (`{ ; }`, `{ {} }`) does not occur in any source (**unknown**; the model treats it as non-empty).

### 2.4 A field initialiser tree

`T f = e;` gives the tree `E(e)`, `end`: the expression with its value used (top node `expr`, not `stmt`), then op 0x10. One tree per declarator that has an initialiser, static or not; a field without initialiser has no tree. The tree is not part of any constructor: constructor trees are reproduced from the constructor body alone, and the interpreter runs a thread on the initialiser tree and takes the value left on the operand stack (opcodes.md, `end`). **Proven**: 2,331 field initialiser trees of the oracle pairs reproduced (1,253 static, 1,078 instance declarators in those sources); `E; end` with exactly one value holds for all 3,117 initialiser trees of the corpus (`check_destruct.py`: 786 without source).

### 2.5 The u16 of a node ("slot")

It is the source line the scanner had reached when the node was built (foundation 3.6); section 8 gives the rule for every kind of node. It "looks constant inside a tree" in the trees one looks at first: all 3,117 field initialiser trees and 275 of the 6,107 method trees with nodes carry a single line value, 3,392 trees in all. It is not a counter and it is not monotonic: the update of a `for` comes behind the body and carries the line of the header, a jump carries the line of the end of its statement.

### 2.6 What the old dumps showed at the top and at the end

"Declaration-like nodes in descending order at the top, matching nodes at the end" are two different things. At the end they are the `release` runs of 2.2, highest index first. At the top they are `local` nodes: a constructor that hands its parameters on, `super( a, b, c )`, pushes them in source order, and because parameters are numbered in reverse (section 3) the indices descend. 2,619 constructor trees open with a super / this call whose arguments are exactly `local` nodes in descending order; 65 trees start with two or more such nodes. Nothing is declared there.

## 3. Locals

The frame holds one list of locals. The compiler knows, at every point, how many are live; call it `live`.

| Rule | Status | Evidence |
| --- | --- | --- |
| Instance methods and constructors start with `this` at index 0; static methods have no such slot and start at 0 with the parameters | proven | 271 `local 0` nodes for the keyword `this`; 70 static methods with code reproduce |
| Parameters follow in **reverse** order: the last parameter has the lowest index | proven | 9,197 `local` nodes that name a parameter are predicted from the name; for 1,779 of them forward numbering would give another index |
| A declaration takes the next index: `declare live`, then `live` grows by one | proven | 3,290 `declare` nodes; 19,146 `local` nodes that name a declared local predicted from the name |
| A local lives from its declaration to the end of the scope it is declared in; the scope end emits one `release` per local of the scope, highest index first, and `live` shrinks | proven | 1,451 releases at block ends, 444 at the end of a `for`, 51 at the end of a case group, 1,344 + 9,291 at body and method end |
| Scopes are: a block `{ }`; a `for` statement (its init declaration); one case group of a `switch`; the method body | proven | all of the above reproduce; 5,047 blocks, 936 of them with locals; 36 case groups with locals |
| Sibling scopes reuse indices | proven | 657 `declare` nodes take an index that a closed scope used before in the same tree |
| `break`, `continue` and `return` emit `release` nodes for the locals they leave behind but do not change `live`: the code behind them is compiled as if they were not there | proven | 63 + 1 + 12,202 such releases; 80 statements stand behind a return / break in the same list and are compiled normally |
| The fifth word of the method row is the highest value `live` reaches (0 for an empty tree) | proven | 5,239 of 5,239 method rows of the oracle pairs from the model; 1,243 of 1,243 method trees of the class files without source from the structure walk |

No node declares or initialises `this` or a parameter; the only nodes that mention them outside expressions are the releases of a return and of the method end. `this` is addressed as `local 0` only where the keyword is written (`this.x` is `local 0`, `getfield "x"`; `f( this )` pushes `local 0`); a bare field or method name of the own class is a `field` / `method` node with no receiver (how names resolve is the expression analyst's subject).

The immediate of `release` is the index of the local it removes. The interpreter does not read it (it pops the last local), so a wrong index would not show at run time, but byte identity needs it: all 24,847 `release` nodes of the oracle pairs are predicted.

## 4. Statement form -> node sequence

Notation: `E(x)` the nodes of expression `x`, leaving one operand; `S(x)` the same nodes with the last one as `stmt` instead of `expr` (section 7); `[s]` the nodes of statement `s`; `R(a..b)` releases from index `a` down to `b` (nothing when `a < b`); `X:` a position that a jump names. `live` and `mark` are numbers of live locals (section 3). Details that the one-line forms leave out:

- **Expression statement.** No node drops the value. The last node of the expression is written with op 0x1008 `stmt` instead of 0x1007 `expr`, and the interpreter body of that kind does not push (or, for a call, pops what the callee returned). The elements of a `for` init and update are compiled the same way. Section 7.
- **Declaration with several declarators** (`int a, b = 2;`, 60 in the oracle sources): one sequence per declarator, in order, each taking the next index.
- **Block.** A block leaves no trace of its own except the releases at its `}`. A block without declarations emits nothing but its statements.
- **if.** `X` is the node behind the then-branch (and behind the `jump Y` when there is an else). An empty branch is legal and gives a jump over nothing: `if (c) {} else {}` is `E(c)`, `jump_false +2`, `jump +1`.
- **for.** The init is a declaration (`declare ..`; 444) or expression statements (`S(i)`; 42) or absent (24); locals of the init are released at `X`, after the loop, so `break` (which jumps to `X`) and the failed condition both run those releases. Without condition there is no `E(c)`, `jump_false` (21; all of them `for(;;)`). The update `S(u)` stands behind the body at `C` and keeps the lines of the header it is written in; without update `C` is the closing `jump T` itself (22).
- **switch.** The subject is evaluated once and stays on the operand stack. Each `case` node pops the case value and the subject and compares; equal: it jumps to its group with the stack empty; different: it pushes the subject back. Behind the last test `pop` drops the subject and `jump` goes to the `default` group, or to the end `X` when there is none (127 of 133 switches have none). The groups follow in source order, each closed by the releases of the locals declared directly in it (a group is a scope: 36 groups declare locals). There is no jump between groups, so a group without `break` runs into the next one.
- **break / continue.** `mark` is `live` at the point the loop or switch was entered (for a `for`: after its init, so the loop variable is not released by `break`). The releases are for the locals declared inside since then; 44 breaks and the one continue of the sources release at least one. `break` in a switch: 488; in a loop: 28.
- **return.** `value` detaches the result from the variable it may refer to before the locals go; then every live local is released, down to `this`, then `ret_value`. A constructor returns with `ret` first and the (unreachable) releases behind it.
- **Unreachable code is kept.** A statement behind `return` or `break` in the same list is compiled like any other (80 in the oracle sources, most of them a `break;` behind a `return`).

Forms of the table that the corpus tests thinly or not at all are listed in section 10.

## 6. Jumps

### 6.1 Encoding

Four opcodes jump: 0x1014 `jump`, 0x1015 `jump_false`, 0x1016 `jump_true`, 0x1017 `case`. The immediate is a **signed 32-bit number of nodes, relative to the jump node itself**: target index = index of the jump + immediate. Forward jumps are positive, backward jumps negative (two's complement in the u32). The unit is the node, not the byte: on disk nodes are 3 or 7 bytes, the loader expands each to an 8-byte record and the interpreter adds `imm * 8` to its program counter (`vmthread_op1014_goto`, old exe 0x423648; `jump_false` 0x423239, `jump_true` 0x423267, `case` 0x423608). A taken jump is not followed by the usual advance, so the offset is not relative to the next node.

`check_jumps.py`, all 9,772 trees, 13,331 jump nodes:

| Check | Holds for |
| --- | ---: |
| J1: the target lies inside the tree (0 .. node count) | 13,331 of 13,331 |
| J2: the target is a node the interpreter dispatches, never a carrier or a path segment | 13,331 of 13,331 |
| J3: the offset is not 0 | 13,331 of 13,331 |
| J4: the offset is the one the statement model computes | 11,401 of 11,401 (every jump of the 7,732 trees reproduced from source) |
| J5: the jump has a role in a statement form, found from the nodes alone | 1,930 of 1,930 in class files without source |

J5 would be worth little if the structure reader accepted anything. `selftest_destruct.py` damages 809 trees it accepts, one node at a time: of 5,448 trees with one jump offset moved by one node it rejects 4,989; the 459 it accepts are other well-formed programs (the moved target is itself a statement boundary, or the `jump_false` now lands on the jump in front of its old target, which reads as `break` / `continue` / a loop without condition). Of 8,119 trees with one `release` or `declare` index changed by one it accepts 0. Of 10,346 trees with one node removed it accepts 175: 143 lost a unary operator or a `getfield` that no jump spans (another well-formed expression), 30 lost an unreachable `release` behind a `return` (the reader cannot know how many locals the compiler still counts there and does not insist on the number), 2 other (the closing jump of a `for(;;)`: straight-line code is a program too).

Every node index is a node boundary, so "lands on a node boundary" is J1 and J2 together. That the rule is the right one among its neighbours shows in the count of jumps whose target would be a dispatchable node under a rival reading:

## 8. Which line a node carries

### 8.1 The rule

A node is built in the action of a grammar rule and stamped with the line the scanner has reached at that moment: the line of the last token the parser has asked for. For a rule that the parser can reduce without looking ahead that is the last token of the construct; for a rule that needs one token of lookahead it is the token **behind** the construct. The nodes are then placed in execution order, which is not the order they were built in: the jump of an `if` is built when the whole statement has been parsed, but stands in front of the body.

With that single idea, and the lookahead behaviour of an LALR(1) parser for the grammar of the Java Language Specification, the line of all 590,101 nodes of the oracle pairs is predicted (and of the 5,322 nodes of the older-build pairs). ### 8.2 `END(statement)` and what it says about the grammar

The jumps of `if`, `while` and `for` are built when the statement is reduced. Which token the scanner has reached then depends on whether the parser needed to look one token past the statement:

```
END(s, dual):
    s is `if` without else:     token behind s                (always: the parser must see that no `else` follows)
    s is `if` with else:        END(else-branch of s, dual)
    s is `while` or `for`:      END(body of s, dual)
    anything else:              token behind s when dual, else the last token of s  (`;` or `}`)

dual is true  for the then-branch of every `if`,
              for the else-branch and for a loop body when the statement they belong to is itself in a dual place;
dual is false for a statement directly in a block, in a case group, in a method body, and for the body of `do`.
```
This is exactly the behaviour of the LALR(1) grammar printed in the Java Language Specification, which avoids the dangling-else conflict with a second set of nonterminals (`StatementNoShortIf`, `IfThenElseStatementNoShortIf`, ...). In the then-branch of an `if` a finished statement can still be either a `Statement` or a `StatementNoShortIf`; the parser has to read the next token (`else` or not) to choose, and it does so before it reduces the statement. Everywhere else a statement that ends in `;` or `}` is reduced at once. A plain yacc grammar with the dangling else resolved by precedence would behave like "END without the context rule", which the oracle refutes (nested `if`/`else` and loops directly in a then-branch).

Further agreement with that grammar: the set of expressions that can be statements is its `StatementExpression` (assignment, pre/post increment and decrement, method invocation, class instance creation; section 7); a constructor body is `{ ExplicitConstructorInvocation(opt) BlockStatements(opt) }`, which is why the implicit super call carries the line of the first token behind the `{` (the parser reads it to see whether an explicit invocation follows) and why a written `this(..)` / `super(..)` carries the line of its `;`. **Inferred** from line numbers, not read from the exe; the yacc tables in the exe can confirm it.

## 11. The emitter, in short

`stmtgen.py` is the reference; this is its skeleton. `emit` appends a node with the line of the given token; `END` is the function of 8.2; `flow` is the stack of enclosing loops and switches.

```
stmt(s, dual):
  block:      m = live; stmt(x, false) for x in s; release live-1..m at `}`; live = m
  T v [= e]:  per declarator: declare live; type T; [init; E(e); store]; live += 1     (line: token behind the name)
  x;          E(x) with the last node as stmt
  if:         E(c); jump_false X; stmt(then, true); [jump Y; X:] stmt(else, dual) [Y:]  (jumps: line END(s, dual))
  while:      T: E(c); jump_false X; push flow(brk X, cont T, mark live); stmt(body, dual); jump T; X:
  do:         T: push flow(brk X, cont C, mark live); stmt(body, false); C: E(c); jump_true T; X:
  for:        m = live; init (declarations or S(e)); T: [E(c); jump_false X];
              push flow(brk X, cont C, mark live); stmt(body, dual); C: S(u)..; jump T; X: release live-1..m; live = m
  switch:     E(v); per case label: E(k); case G; pop; jump Gdefault-or-X;
              push flow(brk X, mark live); per group: G: stmt(x, false)..; release live-1..mark (line: token behind the group); X:
  break:      f = innermost flow;       release live-1..f.mark; jump f.brk      (live unchanged)
  continue:   f = innermost loop flow;  release live-1..f.mark; jump f.cont     (live unchanged)
  return:     constructor: ret; release live-1..0
              else: [E(e); value | push_void]; release live-1..0; ret_value     (live unchanged)

method(m):
  body `;`, or `{}` in a non-constructor: no node at all
  live = 0; instance: this -> 0; parameters last to first -> next indices; P = live
  constructor whose body does not start with this(..) / super(..): push_int 0; super_init; stmt ctor   (line: first token behind `{`)
  stmt(x, false) for x in body
  constructor or void: the return of above, at the closing `}`
  release live-1..P; release P-1..0                                      (line: the closing `}`)
  locals word of the row = highest value live reached

field initialiser:  E(e); end
```

## 12. What this settles in the foundation

No statement of `foundation.md` or `opcodes.md` is contradicted, and no fault was found in `lib/`; the tools are used as they are. Open questions of foundation.md section 7 that are answered here:

- **Question 5, line attribution** of nodes without a token (jumps, releases, the implicit super call): section 8. The observed rule "the update of a `for` carries the line of the header" is a case of the general rule (expression nodes carry the line of their own tokens).
- **Question 6, scopes**: section 3; the release sequence stands twice at the end of a method because the return releases every live local and the two scope ends (body block, method) release them again (section 2.2).
- **Question 7, empty bodies**: section 2.3.
- **Question 8, older builds**, for the statement layer: the 154 trees of the 153 consistent pairs compiled by builds 0x24F5C and 0x11AE1 are reproduced by the same rules, lines included. They are almost all constructors of part scripts, so this says little about loops and switches in those builds.

## 13. Scripts and how to reproduce

All under `compiler/analysis/stmt/`, standard library only, corpus read-only. `python -I run_all.py` runs them in order (about a minute) and rewrites this file; it exits with 1 when a headline number is not the one stated here.

| Script | What it does | Output |
| --- | --- | --- |
| `sparse.py` | Recursive-descent parser of the dialect; every syntax node knows its first and last token | library |
| `parse_all.py` | Parses all sources; census of syntax nodes | `out/parse_all.txt` |
| `check_parsers.py` | `sparse.py` against `lib/parser.py`: same tree, same token spans? | `out/check_parsers.txt`, `.json` |
| `libast.py` | Turns a tree of `lib/parser.py` into the shape `stmtgen.py` reads | library |
| `align.py` | Attributes every tree of a blob to a field or method of the source | library |
| `stmtgen.py` | The model compiler for statements, locals, control flow and lines | library |
| `check_stmt.py` | Emits every tree of every pair with the model and compares node for node; line rules against rivals. `--lib`: on the trees of `lib/parser.py` | `out/check_stmt.txt`, `.json`, `out/check_stmt_lib.*` |
| `destruct.py` | Reads statement forms back from a node sequence, no source | library |
| `check_destruct.py` | All trees of the corpus through `destruct.py`; jump roles against the model; locals word; `stmt` kinds | `out/check_destruct.txt`, `.json` |

| `run_all.py` | Runs all of the above in order and compares the headline numbers | - |

**Parsers.** This study was built on its own parser, `sparse.py`, because `lib/parser.py` did not exist when it started. The emitter needs nothing from a syntax tree but its shape and the first and last token of every node. `check_parsers.py` brings both trees to one canonical form (kind, line and text of the first and of the last token, children) for every source: 3,454 of 3,454 sources give the same tree with the same token spans (0 different). `libast.py` adapts a `lib/parser.py` tree to the shape `stmtgen.py` reads (the one real difference is the dotted name, kept flat here and nested there), and `check_stmt.py --lib` repeats the whole proof on those trees: the report is the same line for line. So the rules of this document apply to the prototype's parser as they stand.

Use from another script:

```python
import sys; sys.path[:0] = [r'...\compiler\lib', r'...\compiler\analysis\stmt']
import oracle, sparse, align, stmtgen
e = oracle.entry('game/Trigger')
unit = sparse.parse(oracle.load_source(e))    # or libast.parse(text): the tree of lib/parser.py
blob = oracle.load_class(e)[0]
for t, kind, node, row, is_static in align.align(unit.classes[0], blob):
    if t is None: continue                      # abstract method: no tree
    g = stmtgen.Gen(unit, blob, blob.trees[t])  # third argument None: free mode, no class needed
    g.field_init(node) if kind == 'field' else g.method(node)
    g.finish()                                  # g.out: predicted nodes (code, imm, ln, cat)
```
