# The script language as the shipped sources use it

Generated by `lib/gen_grammar_md.py` from `lib/grammar.md.in`. The prose and the
EBNF are written by hand; **every number is filled in from the output of a
script** in `lib/`, so the text cannot drift from the proofs. Regenerate with
`python -I lib/run_language.py` instead of editing.

Subject: the dialect of the 3,454 `.java` sources of Street Legal Racing:
Redline, Build 940 (`D:\SLRR-test`, read-only), which the game's own compiler
turns into `.class` files of format TUFA. This document is the language half of
the compiler work: what the scanner and the parser have to accept, and how
often each construct occurs. The class format and the opcodes are in
`notes/foundation.md` and `notes/opcodes.md`.

Evidence standard, as in `foundation.md`: **proven** = a script checks the
statement against the whole corpus and the count is quoted; **observed** = seen
in examples; **unknown** = said outright. A construct with count 0 is called
*never used*: `parser.py` may still accept it, but nothing in the corpus says
what the game's compiler does with it.

## 2. Lexical grammar

`lexer.py` is strict: a character no rule accepts raises `LexError`. Proven by
`check_parse.py`: L1 3,454 of 3,454 sources tokenize; L2 tokens, comments and white
space tile the file for 3,454 of 3,454; L3 the token stream equals that of the
foundation's independent `srclex.py` for 3,454 of 3,454.

### 2.1 Characters and lines

All sources are 7-bit ASCII with CRLF line ends (`corpus.md`). White space is
blank, TAB, CR and LF (the lexer also takes FF and VT). A line number is 1 +
the number of LF characters before the token; the compiler stamps every node
with one (`foundation.md` 3.6). Outside comments and strings only letters,
digits, `_` and the operator characters of 2.8 occur: the lexer has no rule
for `@ # $ \` or a backquote, and rule L1 holds.

### 2.4 Integer literals

```
IntLiteral = Digit { Digit }
           | "0" ( "x" | "X" ) HexDigit { HexDigit } ;
HexDigit   = Digit | "A".."F" | "a".."f" ;
```

| Form | Count |
| --- | ---: |
| decimal | 26,189 |
| hexadecimal `0x` | 464 |
| hexadecimal `0X` | 14 |
| hexadecimal above 0x7FFFFFFF (`0xFFFFFFFF`, `0x80000000`) | 180 |
| decimal with a leading zero (octal in Java) | 0 |
| decimal above 2147483647 | 0 |
| any literal above 32 bits | 0 |

Hex literals have 2, 3, 4, 6 or 8 digits. No `L` suffix exists (it would not
tokenize). The value is the number modulo 2**32 and becomes the immediate of an
`int` carrier node: **proven** for 25,940 of 25,940
int literals in the trees of consistent pairs (`check_shape.py` compares the
value), 478 of them hexadecimal,
180 above 0x7FFFFFFF. A minus sign is
not part of the literal: `-1` is the literal 1 under a unary minus
(388 + 9,220 signed
literals, and 93 with a unary plus).

`check_shape.py` compares float literals by kind and position only
(35,413 of them).

## 3. Syntactic grammar

EBNF: `=` defines, `|` separates alternatives, `[ ]` is optional, `{ }` is
repetition, quoted text is a token. This is the grammar the corpus needs; it
is what `parser.py` implements, minus the alternatives listed in 3.4 that no
source uses.

### 3.1 Declarations

```
Unit            = "package" QualifiedName ";" { Import } { TypeDecl } ;
Import          = "import" [ Identifier ":" ] QualifiedName "." "*" ";" ;
QualifiedName   = Identifier { "." Identifier } ;

TypeDecl        = { Modifier } "class" Identifier [ "extends" Identifier ]
                  [ "implements" Identifier { "," Identifier } ] "{" { Member } "}"
                | { Modifier } "interface" Identifier "{" "}" ;
Modifier        = "public" | "private" | "static" | "final" | "abstract" | "native" ;
Member          = FieldDecl | MethodDecl | ConstructorDecl ;

FieldDecl       = { Modifier } Type Declarator { "," Declarator } ";" ;
Declarator      = Identifier [ "=" Expression ] ;
MethodDecl      = { Modifier } Type Identifier "(" [ Param { "," Param } ] ")" ( Block | ";" ) ;
ConstructorDecl = { Modifier } Identifier "(" [ Param { "," Param } ] ")" ( Block | ";" ) ;
Param           = Type Identifier ;
Type            = ( "int" | "float" | "void" | Identifier ) [ "[" "]" ] ;
```

A member that starts (after its modifiers) with `Identifier "("` is a
constructor; every other member starts with a type.

### 3.2 Statements

```
Block           = "{" { Statement } "}" ;
Statement       = Block
                | LocalDecl ";"
                | StatementExpr ";"
                | "if" "(" Expression ")" Statement [ "else" Statement ]
                | "while" "(" Expression ")" Statement
                | "do" Statement "while" "(" Expression ")" ";"
                | "for" "(" [ LocalDecl | StatementExpr ] ";" [ Expression ] ";" [ StatementExpr ] ")" Statement
                | "switch" "(" Expression ")" "{" { SwitchGroup } "}"
                | "break" ";"
                | "continue" ";"
                | "return" [ Expression ] ";" ;
LocalDecl       = Type Declarator { "," Declarator } ;
SwitchGroup     = ( "case" Expression ":" | "default" ":" ) { Statement } ;
StatementExpr   = Assignment
                | ( "++" | "--" ) Unary
                | Postfix ( "++" | "--" )
                | MethodCall
                | ( "this" | "super" ) Arguments ;       (* first statement of a constructor *)
```

A statement that starts with `int` or `float`, or with
`Identifier [ "[" "]" ] Identifier`, is a declaration; everything else that
does not start with a statement keyword is an expression statement.

### 3.3 Expressions

```
Expression      = Conditional | Assignment ;
Assignment      = Target AssignOp Expression ;                      (* groups to the right *)
Target          = a Postfix that is a name, a field access or an array element ;
AssignOp        = "=" | "+=" | "-=" | "*=" | "/=" | "&=" | "|=" | "^=" ;
Conditional     = Binary [ "?" Expression ":" Conditional ] ;
Binary          = Unary { BinaryOp Unary | "instanceof" Identifier } ;   (* by the levels of 6.1 *)
Unary           = ( "+" | "-" | "!" | "~" | "++" | "--" ) Unary
                | "(" ( "int" | "float" ) ")" Unary                 (* cast to a primitive type *)
                | "(" Identifier ")" UnaryNotPlusMinus              (* cast to a class, see 6.3 *)
                | Postfix [ "++" | "--" ] ;
Postfix         = Primary { "." Identifier [ Arguments ] | "[" Expression "]" } ;
Primary         = Literal
                | Identifier [ Arguments ]
                | "this"
                | "super" "." Identifier Arguments
                | "(" Expression ")"
                | "new" Identifier Arguments
                | "new" ( "int" | "float" | Identifier ) "[" Expression "]" ;
MethodCall      = a Postfix that ends in Arguments ;
Arguments       = "(" [ Expression { "," Expression } ] ")" ;
Literal         = IntLiteral | FloatLiteral | StringLiteral | ResourceId
                | "null" | "true" | "false" ;
```

`UnaryNotPlusMinus` is a `Unary` that does not start with `+`, `-`, `++` or
`--`. Nothing may follow an array creation `new T[n]` directly (no `.`, no
`[`).

## 4. Declarations in detail

### 4.1 Compilation unit, package

Every source starts with `package`; 3,454 of 3,454. The class
name the compiler writes is package + `.` + declared name (rule C1,
2,873 of 2,873). The package does not follow from the directory: 53
packages, 27 of them outside the directory the classpath
gives them (section 7.4), and the class `java.game.track_data` is declared in
21 map directories, `java.game.cars.kit_Custom_body`
in 8 car directories.

3,431 sources declare one type; 23
declare several (up to 9), and the compiler writes one blob per type into the
one class file, in source order (rule U2, 2,819 of 2,819 pairs). The first type is
always named like the file (0
exceptions); the others are not, and 39
of them are `public` (section 8).

### 4.2 Imports

12,392 imports, all of the form `import package.*;`. They are listed in
7.1. `import parts:part.root.BodyPart.*;` occurs 2 times:

### 7.2 How a type name becomes a class name

Type names are always single identifiers. The class file holds full names
(`Ljava.util.resource.ResourceRef;`), so the compiler resolves them.
`symbols.Resolver` does it like this:

1. a class declared in the same source, or another class of the source's
   package;
2. the packages of the imports, in source order;
3. `java.lang`.

Steps 1 and 3 are the **implicit packages**: the own package and `java.lang`
need no import.

Proof: the resolved name equals the name in the class file for every type
name the class file shows: superclass and interfaces (rules C3, C4), field
types (F4, 3,805 of 3,805), parameter and return types (M5, 5,411 of 5,411), and, through
`check_shape.py`, the types of locals, `new`, array creation, casts and
`instanceof` in every tree that agrees (3,293 + 8,241 +
1,814 + 211 + 222 type carriers). In the
sources of the pairs that is 12,707 class type names:
283 found in the same file,
834 in the package,
4,890 through an import,
6,700 in `java.lang`,
0 nowhere.

**The order of the steps is not observable.** Simple class names are unique
among the packages any source can see: of 16,345 type names in all
3,454 sources, 0 have a
candidate in more than one visible package, and 0 resolve nowhere
(that includes the 782 type names of the sources
without a class). Only two simple names exist twice in the corpus at all

engine packages each, never both visible).

What the comparison also proved about emission (the reference is `shape.py`).
The complete emission rules, node for node with jump offsets, local indices
and lines, are the subject of `notes/statements.md`, `notes/expressions.md`
and `notes/declarations.md`, written in parallel by the analyses under
`analysis/`; this list is only what the proof of the grammar needed:

1. A constructor whose first statement is not `this(...)` / `super(...)` gets
   `push_int 0; super_init; stmt ctor` in front.
2. A body whose last statement is not a `return` statement gets an implicit
   return: `ret` in a constructor, `push_void; ret_value` elsewhere. A body
   that ends in `return` gets none.
3. `return e;` is `e; value; ret_value`; `return;` is `push_void; ret_value`
   (or `ret` in a constructor).
4. An expression statement, the init expression and the update expression of
   a `for` use the `stmt` form of their top node; every other node is `expr`.
   Parentheses and unary `+` emit nothing.
5. `if`: condition, `jump_false` to the else part or the end, then-part,
   `jump` over the else part. `while`: condition, `jump_false` out, body,
   `jump` back. `do`: body, condition, `jump_true` back. `for`: init,
   condition, `jump_false` out, body, update, `jump` back to the condition;
   `break` jumps out, and the one `continue` of the corpus (in a `for`) jumps
   to the update. Where `continue` leads in a `while` or `do` is not observed.
6. `switch`: subject; per label the value and a `case` node that jumps to its
   group; `pop`; `jump` to the `default` group or, without one, to the end;
   then the groups.
7. Locals, `new`, array creation, casts and `instanceof` carry the type
   resolved by 7.2; a `declare` with initialiser is followed by the
   expression and `store`.

## 11. The AST

`parser.parse(text)` returns a `Unit`. Every node is a `parser.Node` with
`kind`, `line`, `col`, `end_line`, `tok0`, `tok1` (index of its first and last
token in `unit.tokens`) and the fields of its kind; `node.children()`,
`node.walk()`, `node.to_dict()` and `parser.dump(node)` work on all of them.
The node kinds and their fields are listed in the docstring of `parser.py`.
Three decisions worth knowing:

- Parentheses are kept as `Paren` nodes and a name chain as nested `Field`
  over `Name`; the parser does not decide what a name is.
- A `switch` is a list of `SwitchGroup` (labels + statements), because a group
  is a scope (5.2).
- The token range is on every node because the compiler stamps each emitted
  node with the line its parser had reached (`foundation.md` question 5),
  which is a function of token positions. `op_tok` (operator token of
  `Binary`, `InstanceOf`, `Assign`, `Cond`, `Unary`, `Postfix`) and `name_tok`
  (name token of `Field` and `Call`) serve the same purpose.

The AST is already an interface: `analysis/decl/libbridge.py` and
`analysis/stmt/libast.py` convert it for the declaration and statement models
of the parallel analyses. Field names and token indices should not change
without changing those adapters.

## 12. Open questions

1. **`import parts:part.root.BodyPart.*;`**: accepted by the compiler; what its
   scanner and parser make of the colon is unknown (2 sources). Reading the
   scanner's rules in the exe would settle it together with the float
   conversion (`foundation.md` question 1).
2. **Order of type name resolution** (own package, imports, `java.lang`): not
   observable, no name is ambiguous. A compiler can use any order for these
   sources; a mod that adds a class named like a runtime class would expose
   the difference.
3. **How the compiler finds a class outside the classpath** (7.4):
   266 uses in sources that compiled.
4. **Precedence of `|` against every other level, of `^` and `&` against
   most, of `==` against `<`, of the shifts against `<` and `+`**: not
   observable (the pairs marked `.` in 6.1). Associativity of levels 4 to 8:
   not observable.
5. **`(Name) - x`**: cast or subtraction, not observable (6.3).
6. **Everything in 3.4**: parsed by `parser.py`, never used, so the compiler's
   behaviour (acceptance, emitted code) is unknown; several labels per switch
   group and fall-through are the ones a modder is most likely to write.
7. **Escapes other than `\" \\ \n \t`**, character literals, exponents, `L`
   suffixes: never used.
8. **Which words the scanner reserves** beyond the keywords in use.
